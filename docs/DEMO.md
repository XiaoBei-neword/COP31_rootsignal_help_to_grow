# 现场演示脚本（约 5 分钟）

## 0. 开场前 1 分钟

```bash
python seed_demo.py     # 现场日期变化时重跑一次，保证"距成熟"天数合适（已有记录不会重复写）
python app.py           # 或者直接双击 start.bat，它会自动补账号并打开浏览器
```

浏览器开两个标签页：`http://127.0.0.1:5000/login`，一个留作登录，一个后面用来切换账号。
窗口拉到 1440×900 以上，缩放 100%。

---

## 1. 一句话把问题说清楚（30 秒）

> 小农户最怕的不是不下雨，是**不知道这几天该干什么**。
> 气象 App 告诉你"未来三天有雨"，但它不会告诉你：要不要浇、浇多少、什么时候收、收上来放哪儿。
> 根脉把这条链路打通：**气候异常 → 灌溉决策 → 收获窗口 → 减少产后损失**。

同时指向页面顶部的闭环条：`01 气候异常 → 02 灌溉决策 → 03 收获窗口 → 04 减少产后损失`。

---

## 2. 看板：把天气变成"风险"（60 秒）

登录 `demo_a / demo1234`（玉米·周口·8 亩）。

讲三个点：

1. **不是播天气，是给结论**：综合风险 91「极高」，首要风险是「霜冻 1.5℃」，因为玉米耐受下限是 12℃。
2. **每个数都可复核**：把鼠标移到风险卡上，念出「触发阈值 12℃ / 触发日 11月15日」。
3. **水分平衡那张图**：柱是作物需水 ETc，另一色是有效降水，缺口就是灌溉任务量。
   顺手展开「计算口径」——ET0 用的是 Hargreaves 公式，没有额外传感器也能算。

指一下右下角：`真实 · Open-Meteo · 取数于 xx:xx`。
> 这句话很重要：数据有来源、有时间，不是我们编的。

---

## 3. 灌溉 Agent：给量、给时段、给理由（90 秒）

点底部「进入灌溉决策」，再点「生成建议」——**先别急着看结果，讲加载态**：

> 这一步真的在调大模型。左边是喂给它的依据：3 日需水 5.1 mm、有效降水 1.9 mm、土壤有效水上限 111 mm；
> 右边是它在算。

结果出来后念三行：

- 决策：建议少量补水
- 水量：净 3.8 mm / 每亩 4.7 m³ —— 一亩地只浇不到 5 方水
- 理由：连续 7 天无有效降水，土壤水库在净消耗，所以净需水上调 21%

再补一句差异化：
> 反过来，如果预报 3 天内有暴雨，它会直接给「暂缓灌溉，本轮归零」。
> **该省的省下来，才是节水。**

（若现场未配 LLM Key：页面会提示「未配置大模型 API Key，已使用本地规则引擎」。
不要说"这就是大模型"，直接讲：**这是同一套量化依据的本地兜底，配了 Key 后模型在此基础上做解释和微调**——诚实反而加分。）

---

## 4. 收获窗口：在天气里找一条缝（90 秒）

进「收获窗口与余量调度」。

1. 指窗口：**11月18日 — 11月29日，最佳单日 11月X日**，置信度看预报覆盖程度。
2. 指逐日条形图：越短越适合作业；有降水的日子直接拉满，标「不宜」。
3. 指右侧那个大数字：**可避免损失 135 kg ≈ ¥324**。
   > 算法很朴素：总产 5400 kg ×（常规损失 6.0% − 本方案 3.5%）。
   > 差别只来自一件事：**在对的日子收，收完 5 天不下雨。**
4. 三步调度：抢收排程（多少亩、几天内）→ 干燥暂存（多少吨、田间晾晒还是烘干）→ 余量外运（多少吨、提前几天联系合作社）。
5. 点「保存调度方案」，提示已存档。

退出 → 登录 `demo_b / demo1234`（水稻·荆州）。

> 同一个系统，不同农户。demo_b 看不到 demo_a 的地块、也看不到他的任何一条记录——

再回 `demo_a`，记录还在。

## 6. 收口（30 秒）

> 我们没做新传感器，也没训模型。
> 做的是把**已经存在的气象预报和大模型**，接成一个农户今天就能用的动作序列，
> 并且把结果折算成他真正关心的东西：**少损失多少斤、多少钱**。
> 一个县如果有 10 万亩玉米，这个 2.9% 的损失差，就是粮食。

## 备用方案（出问题时的说法）

| 现场情况 | 处理 |
| --- | --- |
| 没配气象 Key | 页面自动用 Open-Meteo（免密钥真实数据）；若网络也不通，会显示「演示数据（模拟）」黄条，直接说：这是模拟数据，逻辑一致，接上 Key 即真实数据 |
| 没配 LLM Key | 点「用规则引擎生成建议」，讲清"同一套量化依据，模型负责解释与微调" |
| 大模型超时/报错 | 页面会给出人话错误并自动展示规则引擎结果，说：失败可见、可降级，这是工程上的必要设计 |
| 预报覆盖不到成熟期 | 收获页会明确说"预报窗口尚未覆盖成熟期"，并给出预计成熟日——不要硬编数字 |
| 时间来不及 | 只看板 + 收获两页，灌溉一句话带过 |

## 高频提问

**Q：数据是真的吗？**
A：看角标。`真实 · Open-Meteo` 是真接口；`模拟` 是演示数据，页面会持续标注，不会混。

**Q：模型会不会瞎编灌水量？**
A：我们把规则引擎算好的净需水、水利用系数一起塞进提示词，并要求输出 JSON；回来后还会做上限校验（不超过净需水的 1.6 倍 + 6 mm）。模型负责解释与微调，不负责拍数字。

**Q：为什么 ET0 不用 Penman-Monteith？**
A：Penman 需要辐射、风速、湿度、气压全套要素；农户拿不到。Hargreaves 只用最高最低温 + 纬度，FAO 56 明确列为缺测站替代法，误差可接受。

**Q：阈值哪来的？**
A：`data/crops.json` 是通用参数表，已经按作物分开（8 种）。真实落地时应按当地农技站口径校准——这也是我们把它做成可编辑 JSON 而不是写死的原因。

**Q：能推广吗？**
A：现在是单机版，数据在本地 SQLite。要推广需要三件事：气象 Key 配额、村一级的地块档案、以及把"损失率/价格"换成当地实际值。产品形态不用改。
